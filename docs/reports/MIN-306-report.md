## 4. 명세와 다르게 한 것
1. **작업 브랜치**: `min-306-instant-result` 대신 `claude/new-session-awoqnf`에 푸시했다. 이 작업 세션은 지정된 브랜치에만 푸시하도록 설정돼 있다. main 직접 푸시·머지는 하지 않았고 PR로 올렸다.
2. **watchTime "참가 1일" 판단**: `평균` 생략 기준을 `result.stats.validDays`(관람 3개 이상이라 평균에 들어간 날 수)로 했다. 이틀 참가했지만 하루가 3개 미만이면 실제로는 하루 값이라 `평균`을 뺀다.
3. **watchTime·resident %는 내림**: 반올림하면 단계 경계를 넘어 보일 수 있어 둘 다 내림으로 맞췄다 (resident는 명세대로 내림).
4. **streak 보조 줄 채우기**: "중복이면 다음 순서 공연으로 채움"을 ① ★ ② 첫 공연 ③ 마지막 공연 순서로 넣되, 겹치면 구간 안 공연을 시작 시각 순으로 훑어 아직 안 넣은 공연을 넣는 것으로 해석했다 (예: ★가 첫 공연이면 두 번째 공연이 들어감).
5. **2팀 축소**: 같은 우선순위로 2팀만 고른다 (★가 있으면 ★ + 첫 공연, 없으면 첫 + 마지막).
6. **칭호 줄바꿈**: 단어 중간에서 끊기는 크기는 쓰지 않고 더 줄인다. 그래서 실제 최장 라벨("제 메인스테이지는 따로 있습니다")도 3줄이 아니라 작아진 2줄로 그려진다. 한 장에 다 안 들어가면 칭호 크기(80→44) → 간격(20→16→12) 순으로 줄인다.
7. **카드 높이**: Figma 프레임 1066 × 1.8 = 1918.8이라, 1920px을 맞추려고 레이아웃 높이를 1066.7로 잡았다. Figma의 노이즈 그레인 효과는 그리지 않았다.
8. **이벤트 속성 추가**: `gmf_result_shown`에 `restored`(새로고침 뒤 다시 보여준 경우 true), 카드 생성 실패 시 `gmf_card_render_failed { error }` 이벤트를 추가했다. 연락처·한마디 본문은 어디에도 넣지 않는다.
9. **연락처 안내 문구**: 동의 체크박스 문구를 "남긴 연락처로 연락받는 데 동의해요"로 바꾸고, 화면 쪽 검사 메시지만 바꿨다. 서버(`parseSubmission`) 메시지와 검사 로직은 그대로다.
10. **결과 화면 머리글**: 결과 화면에 `결과가 나왔어요`, 피드백 상자에 `30초 피드백`·안내 한 줄, 보낸 뒤 `고마워요!`·안내 한 줄을 넣었다. 칭호·근거 문구는 추가하지 않았다.

미리보기에서는 제출·피드백을 보내지 않았다. 확인한 것은 GET 요청뿐이다 (`eedcc10` 미리보기 기준): `/gmf`가 200으로 새 화면(v0.3)을 주는 것, `/api/gmf-feedback`이 배포돼 405(`POST만 받아요`)를 돌려주는 것. 그래서 **운영 DB에 실제로 INSERT되는지는 확인하지 못했다** (테이블·권한, 미리보기 환경의 `GMF_DATABASE_URL` 모두 미확인). 검수 측 휴대폰 확인에서 처음 생기는 익명 ID를 정리 대상으로 기록해 주세요.

브라우저 흐름 테스트는 로컬 가짜 API로 돌렸다 (그때 쓰인 익명 ID는 DB에 가지 않음).

## 8. 알려진 문제·위험
- **iOS 공유 시트 미확인**: headless Chromium에서는 `canShare({files})`가 거짓이라 다운로드 경로만 탔다. Safari·인스타 인앱에서 공유 시트·저장 동작은 실기기 확인이 필요하다.
- **인스타 인앱 브라우저**: Web Share·`download` 둘 다 막힐 수 있다. 그때는 "이미지를 길게 눌러 저장할 수 있어요" 안내에 기댄다 (`<img>`가 PNG dataURL이라 길게 누르기 대상은 됨).
- **글꼴 로드 지연**: Google Fonts를 4초 기다린 뒤에도 안 오면 기본 글꼴로 카드를 그린다 (Black Han Sans 대신 Noto/시스템 글꼴). 카드가 다르게 보일 수 있지만 실패하지는 않는다. 축제 현장 데이터가 느리면 카드 생성에 몇 초 걸릴 수 있다 ("카드를 만드는 중…" 표시).
- **카드 모서리 투명**: 명세대로 둥근 모서리를 투명으로 뒀다. 사진 앱·스토리 배경에 따라 모서리가 흰색/검은색으로 보일 수 있다.
- **같은 기기 재방문**: 제출에 성공한 기기에서 `/gmf`를 다시 열면 폼 대신 마지막 결과가 먼저 나온다 (기록 고치기로 폼 이동). 제출 후에도 초안(연락처 포함)을 이 기기 localStorage에 남긴다 — 기존에도 제출 전에는 남겼던 값.
- **피드백 1회 제한은 화면에서만**: 서버는 INSERT만 가능해서 중복을 막지 않는다. localStorage를 지우면 같은 결과로 다시 보낼 수 있다.
- **판정 결과가 화면 버전에 묶임**: 판정을 브라우저에서 하므로, 배포 후 판정 규칙을 바꾸면 이미 열린 화면은 옛 규칙으로 계속 판정한다 (`judgeVersion`이 피드백에 함께 저장됨).

## 9. 판단이 필요한 것
1. **resident 도달 난이도**: 하루 최소 12개를 스테이지를 오가며 골라야 하고(전수 탐색 확인), 11개로는 최대 83.6%라 닿지 않는다. 기준 85% 유지 여부.
2. ~~**streak이 너무 자주 대표가 될 가능성**~~ (11장에서 반영): 고정 순서상 streak이 가장 앞이라, 한 스테이지를 하루 종일 본 사람도(MBS 8개) mainPref·oneStage 대신 streak("화장실은 언제 가요?")이 된다. 같은 단계면 streak이 이긴다. 그민페 기준으로 순서를 바꿀지.
3. ~~**"연달아 봤어요" 표현**~~ (11장에서 반영): 겹치는 공연을 고른 경우(스테이지 이동)도 연결 구간에 들어가, 하루 24개 전부 체크하면 "24개 무대를 연달아 봤어요"가 된다. 사실과 어긋나 보일 수 있다.
4. **subPref 조건 중복**: 그민페는 메인 기준선이 33.3%라 subPref 2단계(Δ ≤ −25%p)면 메인 비율이 이미 8.3% 이하다. "메인 20% 이하" 조건은 현재 데이터에선 효과가 없다 (그대로 구현함).
5. **watchTime·resident % 내림** 유지 여부 (4장 3번).
6. **결과 화면 머리글·피드백 안내 문구** (4장 10번) 확정.
7. **새로고침 시 결과 먼저 보여주기**를 유지할지 (8장).
